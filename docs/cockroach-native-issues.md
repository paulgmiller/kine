# Native CockroachDB design issues and mitigations

This is a continuing issue register for the experimental `cockroach://` driver.
Keep entries after mitigation: a workaround changes the consequence, not the
underlying tradeoff. Update validation status when tests or measurements change.
The [driver README](../pkg/drivers/cockroach/README.md) describes configuration,
transaction isolation, key layout, and the supported revision contract.

| Issue | Failure mode or constraint | Mitigation in this implementation | Remaining cost / validation |
| --- | --- | --- | --- |
| Resource revisions differ from etcd's global revisions | A version from one resource cannot position a watch of another resource; cross-resource ranges have no single snapshot version. | Scope the server backend by storage prefix; reject cross-domain ranges and transactions; direct progress responses to individual watches. | Deliberately narrower than generic etcd. Unmodified Kubernetes storage tests and K3s are required compatibility evidence. |
| Resource identity is inferred from key prefixes | The first component below `registry-prefix` defines the domain. Storage layouts with deeper resource prefixes can group multiple resource types in one domain. | Document the exact rule and share counters across namespaces; reserve separate health, compactor, bootstrap, and non-path metadata domains. | A future configurable resource-prefix mapping may be needed for finer separation of grouped/custom-resource layouts. |
| A resource counter is a write hotspot | All writes to one resource serialize on one row, including writes to different namespaces. | Different resource domains use different counter rows; mutation and retention transactions never lock counters for two resources. | One busy resource still has a throughput ceiling. Concurrent-CAS and locked-resource independence tests cover correctness, not production throughput. |
| Different counters are not complete workload isolation | Resources share the SQL connection pool, changefeed workers, process memory, and database capacity. A busy resource can affect another's latency without sharing its row lock. | Keep transactions scoped and stream delivery non-blocking; bound queues and expose metrics. | No per-resource admission control or QoS guarantee. Pool saturation and fairness need load testing. |
| Logical domains are not physical range boundaries | Counter rows can share a Raft range; object and anchor spans can initially share ranges across resources. | Order keys by domain and rely on CockroachDB size/load splitting and normal replica placement. Document `SHOW RANGES` inspection queries. | No explicit splits, hash buckets, scattering, or locality policy. Multi-node physical scaling has not been established by single-node tests. |
| Sequential anchors can hotspot a range | Each resource appends revision metadata at one end of its index span. | Group anchors by resource rather than one global sequence. | This remains a hotspot within a busy resource, and small domains can share a range. |
| Serializable isolation is mandatory | Lowering isolation invalidates the counter/anchor ordering argument. This differs from the PostgreSQL-compatible SQL-log append path's read-committed transactions. | Explicit serializable mutation/read transactions and serializable connection defaults; retry entire transactions on `40001`. | Contention causes retries and tail latency. Read-committed URL override is tested. Ambiguous commits are returned as errors rather than blindly retried. |
| Revision numbers do not directly encode commit timestamps | An application clock or timestamp read during a write transaction can be provisional; a later timestamp can include unrelated later writes. | Insert a small immutable anchor in each mutation transaction; read its exact MVCC timestamp after commit and retain full HLC precision. | One extra metadata row per mutation. Correctness depends on CockroachDB MVCC behavior and integration coverage, not PostgreSQL compatibility. |
| Physical deletes lack the deletion revision in their before-image | The old object's `mod_revision` identifies its last update, not its deletion. | Correlate the changefeed before-image with the same transaction's anchor and use the anchor revision for the delete event. | The decoder must receive and validate both table changes; partial pairs cannot be delivered. Delete/recreate and replay tests cover this. |
| Changefeeds are not globally ordered or exactly once | Independent ranges can interleave messages; recovery can duplicate just one key of a transaction, leaving an apparent orphan object or anchor. | Load baselines at the exact feed cursor, emit only complete contiguous revisions, and retain per-domain HLC watermarks to discard either duplicate half independently. | Buffering and gap detection remain required. Genuine missing pairs are errors, never permission to skip a revision. A one-sided replay followed by a resolved frontier has a dedicated regression case. |
| Resolved frontiers add delivery delay | Waiting for a frontier before every event or before replay handoff delays already-complete changes. | Deliver complete contiguous pairs immediately; stop replay when it reaches the snapshot counter; retain resolved timestamps as recovery checkpoints. | Depends on the invariant of one object mutation and one anchor per revision. Any future multi-object transaction design must change batching semantics. |
| Replay setup adds latency in the list/watch race | A concurrent write may be visible in SQL before the shared feed publishes it; opening a new replay feed needlessly delays that event. | Register before reading the snapshot and capture the shared feed's published revision. Use the registered live subscription directly when it already covers all requested changes. | Historical watches still need a temporary feed. Tight observation-window tests remain important. |
| Descriptor polling delays fresh CDC rows | CockroachDB checks table descriptors above emitted timestamps, normally through periodic polling. | Lock both driver-owned CDC schemas with `schema_locked=true`; disable SQL-result buffering on stream connections. | Schema changes require an explicit unlock/migrate/relock procedure. No online schema migration is implemented in this version. |
| SQL stream cleanup can hide failures indefinitely | `pgx.Rows.Close` drains a command; draining a live changefeed before returning a decoder error can block forever. | Close the dedicated feed connection before closing its rows. | Connection teardown is required on consumer/decoder failure. A regression test rejects an event without canceling the caller's context and requires prompt error return. |
| Feed cursor resets can race new subscriptions | After history loss, moving a live cursor forward could skip writes for subscriptions accepted during recovery. | Reject new watches while the feed is unavailable, cancel existing subscribers on failure, and establish a new counter baseline before accepting subscriptions. | Watch availability briefly drops; clients must retry or relist. Connection-loss/restart tests cover recovery. |
| History is bounded by logical expiration and MVCC GC | An anchor can exist after its referenced object history is unavailable. A long-running replay can outlive retention. | Default logical window is one hour, physical GC retention two hours; translate expired reads/cursors to compacted errors. Do not assume sinkless feeds pin history indefinitely. | Clients outside the window must relist. Changing retention does not restore history already removed. |
| An idle resource's last commit can be older than retention | Reading its latest state at an ancient anchor timestamp would fail even though its current objects are valid. | Read current revisions from a fresh consistent snapshot; use historical anchors only when an older state is actually requested. | Current reads work after idle periods; replaying an ancient mutation can still expire. |
| Kubernetes compaction bookkeeping assumes global revisions | Applying one resource's revision to other resources can invalidate unrelated caches. | Acknowledge explicit compaction without triggering GC; keep global compactor metadata value and response revision at zero. | Six upstream tests and the `WatchFromZero` subtest that require imperative global compaction do not apply. Native retention tests cover the replacement contract. |
| Anchors and CDC have operational cost | Historical metadata grows with write rate; initial/replay feeds and retention scans add database work. | Retain only bounded history plus a boundary anchor; batch TTL expiration; prune per domain periodically; use one shared live feed per instance and bounded subscriber buffers. | Retention scans still inspect anchor metadata. Slow consumers are canceled rather than allowed unbounded memory growth. Large replay/GC workloads need load testing. |
| Empty domains retain metadata | Removing all objects does not permit safely resetting that resource's counter while old clients may still resume watches. | Keep its counter and boundary metadata durable. | Resource-prefix churn can grow metadata even when objects and old history are removed. |
| Existing Kine data cannot be imported implicitly | Switching between endpoint schemes can make existing objects appear absent because the schemas differ. | The native driver rejects databases containing the legacy `kine` table and requires a fresh database. | There is no migration tool. Reverse switching is also unsupported, and the legacy driver has no native-schema guard. A supported transition needs a resource-version and cutover design. |
| Database settings are shared configuration | Peers with different registry or retention assumptions can disagree about supported history or routing. | Persist initialization settings and reject mismatched peers. | Registry and retention changes need a coordinated administrative migration; changing a URL alone is insufficient for an initialized database. |
| Validation is not a production support claim | A single-node database with multiple Kine instances cannot establish database-node failover, range rebalancing, or multi-region behavior. | Opt-in experimental driver pinned to CockroachDB v26.2.x; native race tests, direct/split Kubernetes storage suites, and a K3s API-server smoke test. | Production-scale throughput, multi-node failure/rebalance testing, upgrades, migration from existing Kine tables, and latency SLOs remain outside the evidence collected so far. |

## Validation findings (2026-11-25)

- The dedicated list-at-R / concurrent writes / watch-after-R test passes through
  two Kine instances, including replayed deletion and live handoff.
- The complete selected storage suite passes with direct and split readers.
- Complete applicable direct and split watch suites pass, including strict
  watch-list semantics and slow-consumer checks, without extending upstream
  deadlines. The imperative global-compaction exclusions remain explicit.
- The broader direct-watch run exposed both one-sided replay duplicates and
  an indefinitely draining error path. Per-domain duplicate watermarks and
  dedicated-connection cleanup fix those failures; the reproduction, consumer
  error regression, and complete watch acceptance reruns pass.
- Native driver and bridge integration tests pass with the race detector,
  including counter contention, independent resource locks, TTL/history expiry,
  connection recovery, serializable-default enforcement, and legacy rejection.
- Repository-wide short tests and scoped-driver static checks pass. The new
  native test target is wired into CI with its own prebuilt upstream binaries.
- K3s v1.35.4+k3s1 reached API-server readiness and passed a ConfigMap
  create/update/read smoke test. The full Dockerized CI/load job, secure-TLS
  deployment matrix, multi-node failover/rebalance tests, and production-scale
  throughput/SLO measurements have not been run here.
- These entries describe current implementation evidence, not a guarantee that
  every Kubernetes version or CockroachDB deployment topology is supported.
